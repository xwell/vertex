# RSS 抓取与推送修复

## 行为变更

- RSS 请求失败、HTTP 非 2xx、XML 无效或缺少 RSS channel 时向上抛错，不再伪装为“成功但没有种子”。多个 RSS URL 中只要有源成功，仍继续处理成功源；全部失败时发送 RSS 错误通知，且不更新上次成功时间。
- 有效但没有 item 的 RSS 返回空列表，适用于各站点适配器，不计为失败。
- 仅缓存已校验的 RSS XML；升级前遗留的无效缓存会在本次读取时清除并立即重新请求。
- XML 展示页面中的 `xml-viewer-style` 不再把缓存延长到 310 秒。普通源维持 40 秒，lemon/hhanclub 维持 150 秒，sharkpt 维持 310 秒，保留站点专用请求间隔。
- 同一 RSS 任务内，同一下载器的下一批种子等待上一批完成，每批最多 15 个；不同下载器继续并行。这不是跨所有 RSS 任务的全局并发上限。
- 下载器 API 成功返回时就确定 `add_time`，不再混入后续缓存写入和通知耗时。下载种子文件失败后的链接回退保持不变；无效的自定义替换正则不再被记为添加成功。
- 只有实际抓取成功才清除 RSS 源的失败计数；清零任务及“仍在运行”的跳过不会重置失败记录。连续 5 次抓取失败后，原有的 10 分钟保护性阻塞将正确生效。
- 任务结束时清理超时定时器。任务超时仍不是底层 HTTP 请求的取消信号，仍在运行的抓取会继续由 `isRunning` 防止重复执行。

不修改现有 Cron、任务配置、选择/拒绝规则、每小时推送上限、等待时间和站点专用缓存间隔。发布到进入 RSS 之间的站点侧延迟不由本补丁消除。

## 最长休眠时间修复与升级注意事项

### 判定语义

- `maxSleepTime` 判断本轮与上一轮**成功获取并解析 RSS**的间隔，不是距上次调度、距上次添加种子或距种子发布的时间。间隔严格大于 N 秒才触发（例如 600 秒允许，601 秒拒绝）。
- 成功读取合法空订阅、全部被规则拒绝、没有可用下载器、推送额度已满以及下载器添加失败，均不应把源误判为长期休眠。成功时间在抓取完成后更新，不等待推送结束，也不被后续慢处理的完成时间覆盖。
- 抓取全部失败、仅调度/入队、试运行和手动推送不更新成功时间。多 URL 任务保持任务级判定：至少一个源成功就计为成功，不提供独立的逐源休眠保护。
- 超时恢复时，先把本轮未处理且非冻结的种子落库为 `拒绝原因: 最长休眠时间`，然后建立本轮成功基线；已处理的种子不重复记账。随后周期正常运行。休眠拒绝发生在下载器可用性和额度检查之前，不消耗推送额度。
- 休眠拒绝记录写入失败时不前移成功基线，防止下一轮把尚未成功拒绝的历史种子批量添加。Redis 写入失败时保留本实例的内存基线；重建实例后若无有效持久化记录，重新采用首轮保护。

### 保守迁移策略（重要）

**首次升级后，现有任务若没有新的可信记录，会保护一轮：当轮未处理的非冻结种子会被记录为最长休眠拒绝，不推送；成功建立基线后，后续轮询正常运行。** 这可能跳过当轮刚发布但尚未处理的种子，是避免升级后批量补抓的保守取舍，不会删除下载器中已有的种子。

成功时间使用独立 Redis key `vertex:rss:last_success:<任务ID>`。旧 `vertex:rss:last_time:<任务ID>` 可能将失败误记为成功，`vertex:rss:last_attempt:<任务ID>` 仅反映调度，两者都不作为迁移基线。旧 key 不删除，但不再读取或写入。新任务、Redis 记录丢失/读取失败、无效或来自未来的时间同样启用首轮保护。

新 key 有效时，同一任务 ID 的编辑保存、修改链接和进程重启均沿用该可信记录；单纯保存不刷新时间。长时间停用或持续抓取失败后的恢复仍会触发休眠保护。此策略不能追溯恢复旧版本期间真正的最后成功时间，也不能撤销已经添加的历史种子。

显式手动推送不受订阅首轮保护拦截，但不能替订阅建立成功基线；试运行仅展示匹配结果，也不建立基线。正常获取合法空订阅可以建立基线。未配置或配置为非法数值时，最长休眠使用 600 秒的安全默认值。

## 延迟定位日志

INFO 级别新增或补充：

- 排队超过 1 秒的任务记录 `id`、`排队耗时`；其余排队与总执行耗时见 DEBUG。
- 有待处理种子时记录 `RSS阶段统计`：RSS 获取耗时、过滤耗时、待处理数量。
- `RSS种子阶段`：`发现`、`种子文件下载完成`、`添加完成`/`辅种完成`。日志以 hash 关联，不输出 RSS URL、Cookie 或 passkey。

种子阶段 JSON 字段：

| 字段 | 含义 |
| --- | --- |
| `stage` / `hash` / `client` | 阶段、RSS 中的 hash、下载器别名 |
| `stageMs` | 下载阶段为文件下载耗时；添加阶段为该种子本次处理耗时，包含预检查和文件下载 |
| `discoveredAt` | 本轮 RSS 获取完成时刻；尚未处理的新种子在过滤时关联该时刻，不是持久化的历史首次发现时间 |
| `sinceDiscoveryMs` | 本轮发现后至当前阶段的耗时，包含等待前一批推送的时间 |
| `publishedAt` / `sincePublicationMs` | RSS `pubDate` 与当前阶段距该时间的毫秒数；缺失时为 null |

源的缓存命中/网络请求、缓存间隔和源获取耗时见 DEBUG 日志。

若 `发现` 时 `sincePublicationMs` 已经很大，而 `添加完成` 的 `sinceDiscoveryMs` 很小，应继续检查站点 RSS 的可见时间、上游缓存和轮询周期，而不是只提高下载器并发。复活种、置顶种、重新发布或站点时钟异常可能导致 pubDate 不能代表当前上架时间。API 成功返回时间也不保证等于下载器内部最终创建种子的时间，尤其是链接推送。

## 回归测试

```bash
# Node.js 18 或更新版本；无需 Redis、数据库、站点账号或真实下载器
npm run test:rss
```

测试隔离外部请求和持久化边界，覆盖 HTTP/XML 错误、空订阅、多站点适配器、无效缓存刷新、缓存间隔、多源部分失败、限并发、文件/链接回退、添加时间及队列失败/超时状态。最长休眠测试另覆盖长期错误恢复后阻止批量添加 50 个种子、连续额度用尽/下载器不可用/规则拒绝、首次运行、旧 key 迁移、阈值边界、重建实例、手动推送、数据库与 Redis 故障及时钟回拨。镜像构建工作流在构建前执行这些测试。
