# RSS 空闲资源分配修复

## 目标和适用范围

三个旧模式 `uploadSpeed`（当前上传速度）、`downloadSpeed`（当前下载速度）、`freeSpaceOnDisk`（当前剩余空间）共用一套最终目标准入与跨 RSS 预留账本，但各自优化的资源不同。`leechingCount` 也使用同一套准入保护。配置键不变，界面更新为“空闲上传带宽 / 空闲下载带宽 / 真实可用空间 / 下载负载均衡”。

分配器是**单个 Vertex 进程内全部 RSS 共享**的模块，不是每个源或每批单独重置。下载器别名包含 HDD / SSD / VPS 不再带来隐藏加分；不再封顶分数、对每批份额取整，或使用不满足传递性的排序函数。

这优化的是新任务的接纳份额，不是保证平均文件字节数、实际上传字节或收益等比例。站点需求、种子大小、发布时间、peer、磁盘性能等仍影响上传结果。非 RSS 的手动/监控/其他业务入口，以及多个 Vertex 进程之间，不共享这本账。

## 资源计算

所有速度内部统一为 **B/s**。

- 使用上传、下载即时速度与各自 EMA 的较大者，避免尖峰被 EMA 掩盖，也避免负载刚下降时立即过度加种。
- `sameServerClients` 按无向连通组归并当前运行的实例；同机实例聚合流量、磁盘预留和 POST 并发。单向、间接关联也不能重复花费资源。请只关联确实共享资源的实例；不同磁盘或独立链路不应随意合并。
- `U = max(0, 上传容量 - 已用上传)`，`D = max(0, 下载容量 - 已用下载)`。
- `u = U / 上传容量`，`d = D / 下载容量`。
- 已知 `queuedIO` 时 `I = 1 / (1 + queuedIO / 100)`；没有该指标时使用中性系数 1，不伪造 I/O 余量。
- `S = qB 实际可用空间 - minFreeSpace - 同机待确认磁盘预留 - 已用下载速度 × 30 秒`。
- 每个新下载预留 `b = min(种子大小, 256 MiB)`；未知大小使用 256 MiB。不假定已有文件能额外释放 20% 空间。

| 模式 | 可接纳目标的权重 |
| --- | --- |
| 空闲上传带宽 | `U × d × I` |
| 空闲下载带宽 | `D × u × I` |
| 真实可用空间 | `max(0, S - b) × u × d × I` |
| 下载负载均衡 | `u × d × I / (有效下载数 + 1)` |

权重用于持久的平滑加权轮转。候选集与负载相同时，空闲 500 Mbps、1 Gbps、10 Gbps 的上传模式份额接近 `1:2:20`；下载模式对应各自空闲下载带宽。每次发送前重新校验，因此资源改变、规则变化、实例销毁或预留过期会让未发送的决策取消，并退还相应公平信用。

256 MiB 是适配现有滚动缓冲/删种工作流的**短期准入预留**，不是整颗种子最终可容纳的承诺。30 秒写入余量也不能代替 qB 限速、磁盘告警和删种保护。没有独立的可写空间/吞吐保证时，不应把分配器当作存储配额系统。

## 最终目标保护

先按原有最高优先级、同优先级随机语义选接受规则，再对**实际将接收种子的下载器**预留和校验。规则可指定普通候选列表以外的目标，但不能再靠“先校验 A、后改投 B”绕过 B 的限制。显式规则仍优先于加权分配；目标不可用时拒绝，不悄悄改投其他机器。

每个最终目标检查：

- 仍是当前运行的实例、在线、有完整数值快照；快照成功时间不超过 60 秒，已记录的请求开始时间也不超过 60 秒。旧请求晚返回不能冒充新鲜资源样本。
- 下载器级与 RSS 级上传/下载速度上限（配置为正数时生效），以及新下载数上限。
- 实际剩余空间、保底空间与全部 RSS 未确认预留。
- 新下载有正的上传、下载余量；同机组的 API 添加并发最多 2。
- 每个下载器待确认/待发送账目最多 64，全局等待者最多 128；等待 POST 资格最多 30 秒，未发送预留最长 30 秒。

每个 RSS 仍最多并行准备 15 个种子，但**不是每个源都能同时向同一下载器发 15 个 POST**。逻辑分配与 POST 信号量分离，避免高带宽机器仅因 API 正在忙而丢掉应有份额。所有异步查重、文件准备结束后，临发送再次检查。

常见 JavaScript 接受规则通过 `global.runningClient` 读取到的下载数与可用空间包含待确认 RSS 预留；最后复查时排除本条自身预留。该上下文是资源视图，不是 JavaScript 安全沙箱，也不修改真实 maindata 来制造乐观计数。规则应是无副作用的同步谓词。

辅种复用完整已有数据，不占新下载数与新磁盘块，但仍检查在线、新鲜度、速度上限和共享 API 并发。`onlyReseed` 保持原语义。

## API 结果与账目生命周期

- 下载种子文件、免费/HR 抓取在短期预留之前进行。只有下载文件失败、且尚未发出添加请求时，才允许按原逻辑改用链接。
- 正向 API 状态返回时即确认接纳，先更新预留状态与添加时间，再做 SQLite 等后处理。后处理失败不能被误报为 POST 失败、继而再推送一次。
- 已提交但仍等待 HTTP promise 的请求不因调度超时而释放资源。
- POST 抛错/超时按“远端可能已成功”处理，不向另一台机器重试。保留未确定账目，直到新鲜独立快照观察到 hash，或至少 180 秒后、由宽限期结束之后才开始的刷新确认不存在。
- 成功账目同样等待独立观察；若一直未出现，至少 60 秒之后由更晚开始的新鲜刷新确认缺失，才释放。观察到的任务不与真实下载数、空间重复计数。
- `skipSameTorrent` 在批量历史落库之前也可跨 RSS/目标去重；文件推送同时登记源 hash 与真实 hash。近期 hash 缓存上限 4096，保留最多 10 分钟。
- 下载器对象重建不丢弃已提交/结果未确定账目，旧对象的未发送预留则取消。销毁 RSS 后，已在准备的任务不能继续发送。

**重启限制：账本与公平信用目前不持久化。** 它们在进程重启后不保留，不能宣称 exactly-once。上线/回滚需要停止新调度、等待正在发送和结果未确定的添加完成对账，再重启；不能用重启来强行清空未知结果。现有主数据队列“30 秒看门狗与更长 HTTP 超时不一致、迟到响应仍可写状态”的通用取消问题不属于本修复；分配器仅拒绝过老请求的样本，没有修复那条队列的底层取消。

## 带宽单位与迁移

带宽容量新增 `Mbps` / `Gbps`，新建表单默认 `1000 Mbps`。专用解析器只处理容量字段，不改变 `util.calSize`、磁盘单位、上传/下载限速或规则里的字节单位。

| 填写值 | 内部 B/s | 约合 MiB/s |
| --- | ---: | ---: |
| 500 Mbps | 62,500,000 | 59.6046 |
| 1 Gbps | 125,000,000 | 119.2093 |
| 10 Gbps | 1,250,000,000 | 1,192.0929 |
| 旧 0.5 GiB/s | 536,870,912 | 512 |

旧 KiB/MiB/GiB 设置严格保持字节语义，不把 `0.5 GiB` 自动当成 `0.5 Gbps`。如果用户确认旧数字原意就是 Gbps，应做**显式单位迁移**：保留数字（如 0.5、0.7、2.2），仅将 `uploadBandwidthUnit` / `downloadBandwidthUnit` 从 `GiB` 改为 `Gbps`。不额外除以 8，不按网卡/别名改数字，不改限速、空间、启用状态或接受规则。迁移须与新解析器协调发布，不能提前写新单位让旧版代码误读。

缺省/空容量为 1 Gbps；显式非正数、非数值、不支持的单位或溢出在保存前拒绝，不先销毁现有下载器。

配置应填写可持续吞吐，不应只抄网卡链路速度或机器别名。每台上传与下载分别处理；用户已明确确认原配置数值意图时，应按该意图迁移，不要求为纠正单位重新测速。比如上传 500 Mbps 的机器可填 `500 / Mbps` 或 `0.5 / Gbps`，不能继续填 `0.5 / GiB` 还期待正确空闲量。

接受规则、候选列表、Cron、每小时额度、已有删种规则不自动修改。若大量接受规则强制导向某台 HDD，它们仍会覆盖一般带宽份额；需要明确选择保留定向策略，还是在独立的配置变更中调整规则。不能以分配器修复为由悄悄删规则。

## 日志与验证

INFO 日志 `RSS分配` 记录版本、lease、模式、最终 clientId、forced/reseed、容量/余量、空间预留、有效下载数、权重、ruleId；`RSS添加结果` 记录 accepted / uncertain。此审计不记录 URL、Cookie、密码或种子名称。分配日志代表接纳尝试，应结合结果日志统计实际接纳，强制路由与自由分配应分开统计。

```bash
# 常规 CI：Node.js 18+
npm run test:rss
npm run test:client
```

新增 `test/rss-allocation.test.js` 覆盖单位、230 个独立轮次的 `1:2:20` 分配、并发批次分配、真实 Rss+Client 调用、跨源并发、计数/空间原子预留、同机单向/间接分组、规则强制目标、过期/迟到快照、小种子预检查、辅种、超时未知结果、销毁与重建、成功后数据库失败、真假 hash 去重与日志脱敏。另覆盖用户确认的 0.5 / 0.7 / 2.2 / 1 Gbps 上传容量与 1 / 1 / 2.2 / 1 Gbps 下载容量在空闲同候选集下的份额，防止把 HDD 名称的 10G 当成配置值。旧 RSS 抓取/最长休眠、队列和 Tracker 测试继续运行。

生产 Node 14 缺少 `node:test`，使用依赖隔离的串行测试兼容 runner 做额外验证，不加载生产应用或连接业务存储。兼容测试同时发现并修正原有 Node 14 `ERR_INVALID_URL` 会把无 scheme 的原始输入写进错误日志的问题。

前端全量构建需要先按构建工作流生成忽略版本管理的主题文件。已有数据管理页的 JSX 改成等价 `h(Tag, ...)`，两个原本空的帮助页补上空模板，以消除 Vue 构建阻塞；没有改它们的业务流程。构建输出须指定独立目录，不覆盖在线静态文件。

## 发布检查清单

1. 记录/备份源文件、静态构建产物和配置哈希；逐台确认真实上/下载容量，并列出规则定向流量。单位迁移与代码更新分开审计。
2. 在隔离环境跑全部回归、生产 Node 兼容测试和前端构建。禁止通过加载真实 app 进行“测试”，否则可能启动定时任务、删种等副作用。
3. 安排维护窗口暂停新调度、对账在途添加；确保主数据刷新健康，保留 RSS 成功基线。检查进程/下载器重建对概率删种、缓冲删除状态的影响，不随意触发已启用删除策略的重新初始化。
4. 整体发布新 helper 与所有引用者、对应前端产物，再恢复服务；不要只热替换一个 `Rss.js`。当前 Dockerfile 从远程 git 提交检出源码，本地文件未提交/推送并不会自动进入镜像。CI 新增 `sha-<完整提交哈希>` 镜像 tag 与 `org.opencontainers.image.revision` 标签；发布时核对 revision 并固定镜像 digest，避免直接重启旧容器或误拉到另一个提交的 latest。

   **换容器前必须保留 Redis：** 旧镜像的 RDB 可能在容器根目录 `/dump.rdb`，仅执行 `SAVE` 后重建容器仍会丢失该文件。先停新调度并排空在途任务，执行 `SAVE`，将旧 RDB 备份后迁移到数据卷的 `/vertex/db/redis.rdb`，验证 RSS 成功基线和队列状态；新启动脚本显式使用此路径。此变更不自动启用定期快照/AOF，今后升级仍需在停止前保存。不把旧过期快照当成新快照覆盖当前状态。
5. 首先少量放量，按 clientId/forced/outcome 验证接纳数、剩余带宽、磁盘保底、任务数量、API 延迟与未知结果。确认无 POST 超并发、无针对同一目标的超额预留，再扩展。
6. 回滚同样先停调度、对账在途任务，整体回退代码与静态产物；新增 Mbps/Gbps 配置若回退到旧解析器，必须换算回旧字节单位或恢复备份。保留未知结果记录，不靠重复推送探测成功与否。
